# Валидность измерения в движке: атрибуция цели по намерению + гейт пре-айма

**Дата:** 2026-07-15
**Статус:** дизайн, готов к плану
**Фаза:** 3 (движок; независима от Фазы 2B — пересекается только контрактом версионирования)

## Цель

Убрать из движка два дефекта, из-за которых числа отчёта тихо меряют не то, что
заявляют:

1. **Подмена цели между кадрами** — `consistency` и `bias` считаются по потоку
   кадров без идентичности, поэтому смена врага под прицелом засчитывается
   игроку как разброс его механики.
2. **Пре-айм по неотстреливаемым появлениям** — вердикт «прицел ниже линии
   головы» выносится в том числе по врагам, мелькнувшим у края экрана.

Оба дефекта — про валидность, а не про удобство: они не падают, не логируются и
дают правдоподобно выглядящие числа.

## Управляющий принцип (наследуется)

Числа считает ТОЛЬКО движок; VLM объясняет, но не измеряет. Отсюда следствие,
определяющее границы этой спеки: **если сигнала в данных нет, движок молчит, а
не догадывается**. Детектор видит только головы — не оружие, не HP, не то, кто
кого заметил.

## Диагноз (что именно сломано)

### A1. Идентичность теряется по дороге к метрикам

`pick_target` (`aim_metrics.py:95`) на каждом кадре независимо берёт голову,
ближайшую к центру. `analysis_pipeline.py:118` строит из этого `samples`,
`report.py` кормит ими `_consistency_finding` и `_bias_finding`, а
`profile_store.build_clip_record` — продольный профиль.

У эпизодов идентичность есть (трек), у `samples` — нет. При двух врагах цель
может смениться между соседними кадрами, и в ряд radial'ов влетает скачок. Он
попадает в `std_hu` — главный вход диагноза «повторяемость vs калибровка»
(`consistency.py:43`). То есть диагноз механики игрока зависит от числа врагов на
экране.

**«Ближайшая» — плохой прокси для «та, которую игрок ведёт».** Он разваливается
именно там, где игрок действует осознанно: заход в спину, пропуск противников
ради мультикилла, выбор наиболее сложной цели первой. Геометрия скажет
«ближний», игрок вёл дальнего — движок засчитает промах в 12 HU по врагу,
которого игрок сознательно игнорирует. Это не шум, а выдуманная ошибка.

### A3. Пре-айм считает всех подряд

`compute_placement` (`placement.py:61`) берёт каждый эпизод, включая
`unengaged` — врага в 15 HU у края экрана, которого игрок не собирался
стрелять. Он получает вердикт `below` и входит в `mean_dy_hu`
(`placement.py:80`) через `statistics.mean` — среднее без защиты от выбросов.
Счётчик «N из M ниже линии головы» — главный тезис пре-айма на фронте.

### Сопутствующее: инверсия слоёв

Шесть модулей `engine/` импортируют корневой CLI-скрипт `aim_metrics.py`, а он
импортирует `engine.clip_context`. Ядро геометрии (`Head`, `FrameSample`,
`sample_frame`, `pick_target`, `compute_passport`) живёт в CLI. Мы всё равно
трогаем эти швы — чиним попутно.

## Скоуп

**В этой спеке:** A1 (атрибуция по намерению), A3 (гейт пре-айма), переезд ядра
геометрии в `engine/`, версионирование методики.

**Явно вне:**

- **Гейт живого геймплея** — смерть, спектейт, killcam, закупка меряются как аим
  игрока. Требует нового сигнала из видео (HUD/состояние раунда), своего
  детектора, калибровки и холдаута. Отдельная фаза.
- **Статистическая честность** — кадры внутри дуэли автокоррелированы, а
  `_confidence` (`report.py:44`) сравнивает сырое число кадров со
  `MIN_DUEL_FRAMES_FOR_DIAGNOSIS = 100`; эффективная выборка в разы меньше, то
  есть «диагноз» выдаётся на данных гипотезы. Отдельная фаза.
- **Шум HU-нормировки** — `sample_frame` делит на `head_height_px` того же
  кадра, дрожание детектора впрыскивается в `dx_hu`/`dy_hu`; медиана высоты по
  треку это лечит. Отдельная фаза.
- **Вердикт о правильности приоритета целей** — см. «Нормативная сторона» ниже.
- **Гейт `correction` по атрибуции** — сейчас `flick`-эпизод может быть врагом,
  вошедшим в прицел сам; атрибуция даст сигнал это отсечь, но это следующий шаг.
- Фронт, каталог дриллов, коуч, промпт, валидатор.

## Архитектура

```
heads_by_frame → segment_episodes → episodes
                                       ↓
                             attribute_targets()        ← НОВЫЙ ШОВ
                                       ↓
                     поток AttributedSample: 1 трек на кадр
                        ↓             ↓              ↓
                  consistency       bias       profile_store

placement, correction, flick_phase — читают episodes напрямую (они по-трековые)
```

Новые модули:

- **`engine/geometry.py`** — ядро: `Head`, `FrameSample`, `sample_frame`,
  `pick_target`, `MIN_HEAD_PX`, `DEFAULT_DUEL_HU`, `AimPassport`,
  `compute_passport`. Механический переезд из `aim_metrics.py`, числа не
  меняются.
- **`engine/attribution.py`** — слой атрибуции (ниже).

`aim_metrics.py` остаётся CLI + адаптерами источников (`iter_gt_samples`,
`iter_yolo_samples`) и реэкспортирует имена из `engine.geometry`, чтобы
существующие импорты и тесты не сломались. `samples_from_heads` из пайплайна
уходит.

**Свойство, которое сохраняем:** движок считает метрики только по детекциям,
**без декодирования видео**. Оценка камеры по фону (оптический поток) точнее, но
втащила бы чтение кадров в метрический путь — сейчас видео читает только
`evidence_frames`. Сознательно не берём.

## Компонент 1: атрибуция по намерению

### Оценка движения камеры

Все головы смещаются на экране совместно от поворота камеры, плюс каждая — от
своего движения. Значит на кадре N по трекам, живым и на N−1:

```
camera_shift = median(смещений голов в px)     # медиана, не среднее
residual_h   = смещение головы h − camera_shift # собственное движение врага
```

Медиана — чтобы один стрейфящийся враг не утащил оценку.

**Идентифицируемость.** Оценка камеры возможна только при 2+ головах — и это
ровно те кадры, где вообще есть вопрос атрибуции. Задача даёт инструмент там,
где ставит проблему. При 1 голове вопроса нет: она и есть цель.

**Честное ограничение:** при ровно 2 головах медиана из двух = среднее, и стрейф
одного врага пролезает в оценку камеры наполовину. Отсюда `camera_confidence`:
`diagnosis` при 3+ головах, `hypothesis` при 2, `insufficient` при 1 (не нужна).

### Намерение

Для головы в позиции `p` относительно центра при камерном смещении `c`:

```
intent(h) = (|p| − |p + c|) / head_height_px * fps      # HU/с, закрытых КАМЕРОЙ
```

Положительное — игрок ведёт прицел к этой голове. Величина не зависит от того,
идёт ли враг сам: собственное движение врага в `c` не входит.

### Правило выбора

Намерение накапливается по окну `INTENT_WINDOW_S`, чтобы одиночный кадр шума не
переключал цель.

- **Цели нет** → берём кандидата с максимальным намерением выше
  `MIN_INTENT_HU_S`. Если камера стоит и намерения ни у кого нет → ближайшая
  голова (вырожденный статический случай).
- **Цель есть, видна** → держим её, пока другой кандидат не опередит её по
  намерению на `SWITCH_MARGIN_HU_S`. Тогда переключаемся **немедленно**.
- **Цель исчезла** → ближайшая по намерению; если намерения нет — ближайшая.
- **Удержание** → камера почти стоит (`< DWELL_MAX_CAMERA_HU_S`), цель в
  дуэльной зоне: цель держится, переключения нет.
- **Спор** → два кандидата в пределах `CONTESTED_MARGIN_HU_S` и текущей цели
  нет, ЛИБО камеру оценить не удалось при 2+ головах: кадр помечается
  `contested`, из механических статистик исключается и **считается**.

**Гистерезис защищает от неоднозначности, а не от намерения.** Решительный флик
к другой голове — это большое камерное намерение, он переключает цель сразу.
Дребезг «кто сейчас на полпикселя ближе» камерного намерения не создаёт и цель
не двигает. Это принципиально: игрок, фликающий между целями по своему
приоритету, должен измеряться корректно, а не подавляться сглаживанием.

### Контракты

```python
@dataclass(frozen=True)
class AttributedSample:
    frame_idx: int
    track_id: Optional[int]        # None = contested
    dx_hu: float
    dy_hu: float
    radial_hu: float
    head_height_px: float
    switch: bool                   # первый кадр новой цели
    contested: bool

@dataclass(frozen=True)
class AttributionResult:
    samples: Tuple[AttributedSample, ...]
    choices: Tuple[TargetChoice, ...]
    switches: int
    contested_frames: int
    camera_confidence: str         # diagnosis | hypothesis | insufficient

def attribute_targets(episodes: Sequence[Episode], ctx: ClipContext,
                      duel_hu: float = DEFAULT_DUEL_HU) -> AttributionResult
```

`consistency` и `bias` потребляют `samples` с `track_id is not None`.

В `values` находки `consistency` добавляются `switches`, `contested_frames`,
`camera_confidence` — движок честно показывает, сколько кадров было спорных,
вместо того чтобы молча смешивать врагов.

## Компонент 2: выбор игрока как факт (описательно)

### Нормативная сторона — почему её здесь нет

«Правильно ли игрок выбрал приоритет целей» — вопрос об **угрозе**, а угрозы в
наших данных нет: детектор видит только головы, не оружие, не HP, не то, кто
кого уже заметил. Вердикт о правильности приоритета был бы догадкой в обёртке
чисел, а VLM её красиво обосновал бы — ровно тот сценарий, против которого
построен проект.

Частично наблюдаема **сложность**, но не угроза: дистанция через размер головы,
поперечная скорость головы (стрейфящаяся цель труднее), угловое удаление.

### Что движок пишет

Факты выбора, без вердикта:

```python
@dataclass(frozen=True)
class TargetChoice:
    track_id: int
    from_frame: int
    to_frame: int
    chosen_at_radial_hu: float          # как далеко была цель в момент выбора
    head_height_px: float               # прокси дистанции
    lateral_speed_hu_s: float           # прокси стрейфа (по residual, не камере)
    switch_cost_frames: Optional[int]   # кадров от переключения до входа в дуэль
```

В отчёт едет **top-level блоком `target_choices`, не находкой**: у находок есть
критерии и дриллы, а здесь вердикта нет и быть не должно. Это база для будущей
нормативной фазы, когда появится сигнал об угрозе.

Схема отчёта: `SCHEMA_VERSION` 1.1 → **1.2** (аддитивно: новый top-level ключ +
новые ключи в `values` у consistency).

## Компонент 3: гейт пре-айма

Новая ручка `PLACEMENT_MAX_BIRTH_HU`: в пре-айм идут только появления в пределах
N HU от прицела на кадре рождения трека.

**Почему гейт по дистанции, а не по вовлечённости.** Очевидный гейт «считать
только тех, с кем была дуэль» вносит survivorship bias: он выкинет ровно те
случаи, где пре-айм был так плох, что дуэль не состоялась — метрика станет тем
чище, чем хуже играет игрок. Гейт по дистанции этого изъяна не имеет: враг,
возникший в 5 HU и прозёванный, засчитается как провал пре-айма. А враг,
вышедший в 20 HU через весь экран, — вопрос позиционирования и осведомлённости,
а не пре-айма.

Изменения в `values` находки `placement`:

- `mean_dy_hu` — остаётся ключом (не ломаем фронт и `build_criterion` Фазы 1), но
  считается по отфильтрованному множеству;
- `median_dy_hu` — добавляется, устойчив к выбросам;
- `total_seen` / `total_gated` — сколько появлений движок видел и сколько зачёл.

`total` (вход `build_criterion` для placement) = `total_gated`.

**Ожидаемое следствие, а не баг:** `_confidence(rep.total_episodes,
MIN_EPISODES_FOR_DIAGNOSIS)` считается от отфильтрованного числа, поэтому на
части клипов пре-айм честно опустится с диагноза до гипотезы. Это и есть
правильное поведение: раньше уверенность держалась на эпизодах, которые к
пре-айму отношения не имели.

## Компонент 4: версионирование методики

`build_clip_record` (`profile_store.py:62`) складывает в `profiles/{player_id}.json`
уже посчитанные агрегаты — сырых сэмплов там нет, **и нет версии методики**.
После этой спеки определения `mae_hu` и `placement.below` меняются: старые записи
останутся по прежней методике, новые придут по новой, `aggregate_profile`
смешает их. Пересчитать историю нельзя — нужен повторный прогон YOLO по видео,
которого может уже не быть.

Хуже: Фаза 2B считает кумулятивную дельту от anchor'а из истории к текущему
клипу и отрапортует «улучшение» или «регресс», которые на деле — наш рефакторинг.

Решение:

- константа `METRICS_VERSION` в `engine/`; `build_clip_record` штампует ею запись;
- записи без поля = версия 1;
- `aggregate_profile` берёт только записи текущей версии, отброшенные называет в
  `confidence_reason`: «клипов по прежней методике: N — в сравнение не входят»;
- **контракт для Фазы 2B:** `build_clip_snapshots` фильтрует историю по
  `metrics_version`, иначе anchor-серии посчитают смену методики за прогресс
  игрока.

На момент написания `profiles/` в рабочей копии нет — миграция пока
теоретическая, поэтому механизм дёшево заложить сейчас.

## Ручки и их некалиброванность

`dataset1/` в рабочей копии отсутствует, поэтому **новые пороги не откалиброваны
на реальном геймплее**. Значения ниже — обоснованные дефолты, проверенные
синтетикой. Каждый помечается в коде как некалиброванный; калибровка — отдельная
задача, когда появятся клипы (как это было с `conf=0.4` на холдауте).

| Ручка | Дефолт | Обоснование |
|---|---|---|
| `INTENT_WINDOW_S` | 0.05 | ~3 кадра при 60 fps: гасит одиночный шум, не мешает флику |
| `MIN_INTENT_HU_S` | 8.0 | ниже — шум оценки камеры; ср. `MIN_FLICK_SPEED_HU_S = 20` |
| `SWITCH_MARGIN_HU_S` | 6.0 | запас, при котором новый кандидат явно опережает текущий |
| `CONTESTED_MARGIN_HU_S` | 3.0 | ближе — движок не решает, а признаёт спор |
| `DWELL_MAX_CAMERA_HU_S` | 4.0 | «камера почти стоит» = удержание |
| `PLACEMENT_MAX_BIRTH_HU` | 8.0 | ~20% высоты экрана при 1080p; дуэль = 3 HU |

Пороги временные в секундах/HU-в-секунду — как везде в движке, чтобы 30 и 60 fps
оставались сравнимыми.

## Проверка

Синтетика, без видео и БД — по образцу существующих тестов движка:

- **Фланговый мультикилл:** ближний враг в 2 HU игнорируется, камера идёт к
  дальнему в 12 HU → атрибуция уходит за камерой к дальнему. Это тест на
  исходный дефект.
- **Осознанный флик** между целями переключает цель немедленно.
- **Дребезг близости** (другой враг стал чуть ближе без камерного движения) цель
  не переключает.
- **Стрейфящийся враг** не крадёт цель: собственное движение врага не создаёт
  намерения.
- **Спор** помечается и считается, а не разрешается монеткой.
- **camera_confidence:** 1 голова → insufficient, 2 → hypothesis, 3+ → diagnosis.
- **gt и yolo** дают одинаковую атрибуцию на одних треках.
- **Гейт пре-айма** не прячет прозёванного близкого врага (анти-survivorship) и
  отсекает дальнего.
- **Версия:** запись без `metrics_version` не входит в агрегат, причина названа.
- **Регрессия:** переезд геометрии не меняет ни одного числа; существующие тесты
  движка зелёные без правок.
- **Граница фронта:** схема 1.2 аддитивна, `npm run build` не падает.

## Порядок работ

1. Переезд ядра геометрии в `engine/geometry.py` + реэкспорт (чисто механически,
   числа не меняются — отдельный коммит, чтобы диффа следующего шага читалась).
2. `engine/attribution.py` + тесты (оценка камеры → намерение → правило выбора).
3. Проводка: `consistency`/`bias`/`profile_store` на `AttributedSample`;
   `samples_from_heads` удаляется.
4. `target_choices` в отчёте, схема 1.2.
5. Гейт пре-айма.
6. `METRICS_VERSION` + фильтр агрегации.
7. Зелёный прогон + verify фронта.
