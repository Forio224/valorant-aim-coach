# Дизайн: детерминированный каталог дриллов + петля прогресса

**Статус:** УТВЕРЖДЁН (решения приняты 2026-07-05, см. «Принятые решения»);
доменные правки имён/соответствий каталога пользователь вносит поверх.
**Дата:** 2026-07-05. **Область:** тренировочный план коуча (`coach/`, `engine/report.py`, frontend `DrillTable`).

## Проблема

Сейчас каждый дрилл — свободный текст, который VLM сочиняет с нуля: `name`,
`platform`, `dose`, `success_criterion`. `coach/validate.py` проверяет только,
что `target_metric` существует среди findings; **название упражнения и
числовой критерий не проверяются вообще**. На артефакте `b5_friend_clip2.png`
критерии успеха забиты сырыми VLM-числами («−5.265 HU», «1.438 HU»,
«−0.031 HU на следующем клипе»). Это тихое нарушение управляющего принципа
проекта — «числа считает ТОЛЬКО движок». История метрик по клипам уже копится
(`engine/profile_store.py`, `clips: {clip_id: record}`), но не используется для
«сработал ли прошлый совет».

## Метрики движка (факт из `engine/report.py`)

Ровно 4 finding-метрики, каждая с `values` и `confidence`:
- `placement` — values: total, below, above, on_line, band_hu, mean_dy_hu; порог `MIN_EPISODES_FOR_DIAGNOSIS=8`.
- `consistency` — mae_hu, std_hu, iqr_hu, p95_hu, duel_frames; порог `MIN_DUEL_FRAMES_FOR_DIAGNOSIS=100`.
- `bias` — y_bias_hu, x_bias_hu, x_abs_hu, y_abs_hu, duel_frames; порог 100.
- `correction` — flicks_total, flicks_analysed, x/y_over/undershoots; порог `MIN_FLICKS_FOR_DIAGNOSIS=6`. Уже несёт caveat «прокси по output-space».

## Механика (закрывает нарушение принципа)

Разворачиваем поток: движок владеет каталогом и числами, VLM выбирает и объясняет.

```
VLM возвращает по дриллу: drill_id + priority + rationale (+ dose_override?)
      ↓
движок: CatalogDrill по drill_id → name/platform/dose (детерминированно)
      + SuccessCriterion из values соответствующего finding (число считает движок)
      ↓
собирает финальный Drill → отчёт
```

VLM больше не производит ни названий, ни чисел. Его выход сокращается (бонус к
работе по токенам, см. [[coach-token-cost]]).

### Изменения по модулям

- **`coach/drill_catalog.py`** (новый): `CatalogDrill`, `CriterionRule` (3 типа),
  стартовый каталог `metric → [CatalogDrill]`, `assemble_drill(selection, finding)`.
- **`coach/schema.py`**: VLM-выход ужимается до
  `DrillSelection {priority, drill_id, rationale, dose_override?}`; финальный
  `Drill` собирает движок.
- **`coach/validate.py`**: проверка `target_metric` → `drill_id` есть в каталоге
  **и** его метрика есть среди findings; `rationale` по-прежнему через
  HU-groundedness. Дыра «числа в дриллах» исчезает — чисел от VLM нет.
- **`coach/prompt.py`**: инжект «меню» каталога (id + название + метрика) +
  правило «выбирай id, не изобретай упражнения/числа».
- **`coach/client.py` / pipeline**: сборка финальных дриллов после парса.
- **frontend `DrillTable`**: критерий приходит готовой строкой; «главный дрилл» наверх.

### Правила критерия успеха (детерминированные)

Движок применяет к `values` finding-а:
- `placement` → `CountReduction(below, total, 0.2)` + `|mean_dy_hu|`→0.
- `consistency` → `RelativeImprovement(mae_hu, ↓, 0.15)` = «MAE < base·0.85 HU».
- `bias` → `AbsoluteThreshold(|y_bias_hu|, <, 0.5·base)`.
- `correction` → **направленный, не порог** (прокси-метрика; жёсткий порог = ложная точность).

Критерий отдаётся строкой (UI) и структурно `{metric, value_key, comparator,
target, baseline}` — структура нужна этапу 2 для машинной сверки на след. клипе.

### Правило честности плана

Движок: если среди findings нет ни одного `diagnosis` — план урезается до
топ-1–2 по серьёзности + CTA-caveat «запиши ещё 1–2 клипа». Случай скриншота
(4 гипотезы → сейчас 4 дрилла). Честнее + retention-петля, кормящая этап 2.

## Стартовый каталог (сценарии и пороги выверены по Voltaic S4)

Имена и пороги подтверждены актуальными данными Voltaic S4 (evxl.app, 2026-07).
Открытый доменный вопрос — только соответствие «метрика↔семейство сценария».
Тиры используются прогрессией Фазы 2 (рост сверх критерия с confidence → tier+1).

**Семантика тиров = сложность механики в тренажёре** (перенос в игру меряет
движок на клипах, а не сам дрилл — это отдельная ось, см. Фазу 2):
- **tier 1 — Основа (Voltaic Novice).** Пороги новичка; изолированное движение,
  минимальная дисперсия.
- **tier 2 — Закрепление (Voltaic Intermediate).** Выше темп / точность /
  амплитуда; повторяемость под давлением.
- **tier 3 — Мастерство (Voltaic Advanced).** Высокие требования, близко к
  соревновательной механике. Верхняя ступень прогрессии коуча.
- **placement — исключение:** у Voltaic нет пре-айм-сценария (это game-sense),
  поэтому все его тиры — in-game (Range → clear-angles → Deathmatch).

Имена и пороги — **актуальный бенчмарк Voltaic S4** (KovaaK's), выверены по
evxl.app. Ключ: **тиры Voltaic Novice / Intermediate / Advanced = наши
tier 1/2/3**, а семейство сценария тянется через все тиры под одним корнем +
суффикс сложности (`VT Pasu Rasp Novice → … Intermediate → … Advanced`). Внутри
статики сложность растёт ещё и уменьшением числа целей (`1w6ts → 1w5ts → 1w3ts`).
Есть 4-й **неофициальный** тир **Elite** (6 рангов GM→Eclipse) — вне 3-тировой
прогрессии коуча, как endgame-потолок для энтузиастов.

| Метрика | tier 1 · Novice | tier 2 · Intermediate | tier 3 · Advanced |
|---|---|---|---|
| placement *(in-game)* | Range: pre-aim walk на уровне головы, без стрельбы | Valorant «clear angles» — пре-айм типовых углов сайта | Valorant Deathmatch — пре-айм под движением/давлением |
| consistency *(static, повторяемость)* | **VT Multiclick 120 Novice** | **VT Multiclick 120 Intermediate** | **VT Multiclick 180 Advanced** |
| bias *(static, смещение)* | **VT 1w6ts Rasp Novice** | **VT 1w5ts Rasp Intermediate** | **VT 1w3ts Rasp Advanced** |
| correction *(dynamic, флик/перелёт)* | **VT Pasu Rasp Novice** | **VT Pasu Rasp Intermediate** | **VT Pasu Rasp Advanced** |

Второй дрилл correction (по желанию) — семейство **VT Bounceshot**
(Novice/Int/Advanced): реактивный флик по отскоку.

**Опциональный блок — трекинг (доп-тренировка, не основной путь).**
Метрики движка — про клик, поэтому трекинг НЕ привязан к finding'у. Подключается
по симптому «плавность / рывковость микрокоррекций» (высокая дисперсия у
`consistency` или дрожь при гашении флика у `correction`; в Фазе 2 — по
`settle_jitter_hu`):
- плавность → **VT Smoothbot Novice**, **VT PreciseOrb Novice** (precise tracking)
- реактивная коррекция направления → **VT Plaza Novice**, **VT Air Novice** (reactive)

Тир трекинг-дрилла берём по симптому (обычно Novice/Intermediate). Механика:
движок добавляет 1 трекинг-дрилл как `supplementary` (без числового success-
критерия — трекинг не в output-space метрик), VLM объясняет «для плавности»,
приоритет ниже основных.

Замечания к каталогу:
- **placement in-game** (у Voltaic нет пре-айм-сценария) — ответ на красный флаг
  «не спутан ли placement с tracking».
- **`bias` и `consistency` делят static clicking** (Multiclick vs 1wNts Rasp):
  у Voltaic нет категории «систематическое смещение» — это сигнатура ошибки
  внутри статики. Разводим фокусом инструкции: Multiclick = сустейн-повторяемость,
  1wNts Rasp = точная одиночная постановка (видно смещение).
- **Switching-категория** (`VT psalmTS/skyTS/evaTS/bounceTS`) пока не в маппинге —
  резерв для tier-3 переноса `correction` (флики-переключения), если понадобится.

Красные флаги для ревью: (1) бьют ли сценарии по метрике; (2) устраивает ли
деление static clicking между `bias` и `consistency`; (3) достаточно ли 3 тиров
или подключать Elite как tier 4 для про-игроков.

### Пороги Voltaic = объективный критерий tier-перехода

Тиры Voltaic = наши tier'ы; ранги внутри тира:
- **Novice** → iron / bronze / silver / **gold**
- **Intermediate** → platinum / diamond / jade / **master**
- **Advanced** → grandmaster / nova / astra / **celestial**
- **Elite** (неоф.) → gm / nova / astra / celestial / ascended / **eclipse** (6) — вне прогрессии коуча

Пороги под сценарии каталога (Voltaic S4, evxl.app; жирным — верхний ранг тира =
«закрыть тир»):

| Семейство (метрика) | Novice: iron/bronze/silver/**gold** | Intermediate: plat/dia/jade/**master** | Advanced: gm/nova/astra/**celestial** |
|---|---|---|---|
| Multiclick (consistency) | 1160/1260/1360/**1460** | 1360/1460/1560/**1660** | 1630/1770/1890/**2000** *(→180)* |
| 1wNts Rasp (bias) | 650/750/850/**950** *(1w6ts)* | 1000/1100/1200/**1300** *(1w5ts)* | 1280/1380/1460/**1580** *(1w3ts)* |
| Pasu Rasp (correction) | 550/650/750/**850** | 750/850/950/**1050** | 940/1040/1120/**1270** |
| Bounceshot (correction alt) | 500/600/700/**800** | 600/700/800/**900** | 800/900/1000/**1150** |

**Критерий tier-перехода** (независим от HU-чисел движка):

> tier N «пройден», когда игрок берёт верхний ранг тира на сценарии метрики:
> Novice→**Gold**, Intermediate→**Master**, Advanced→**Celestial**.

Даёт **два независимых сигнала** прогрессии: (а) HU-критерий движка на клипах
Valorant (перенос в игру), (б) Voltaic-ранг в тренажёре (механика). Совпали →
уверенное `tier+1`; расходятся → caveat, а не молчаливое повышение. Балл
Voltaic **подтягивается автоматически** по Steam ID из KovaaK's API (Фаза 2,
компонент D) → это измеренный, а не self-reported вход.

Имена/пороги — актуальный S4 (evxl.app, 2026-07); при смене сезона пересверить
один раз через тот же источник или KovaaK's API.

**Балл Voltaic можно НЕ вводить руками — есть публичный API.** KovaaK's
webapp-backend отдаёт прогресс по Steam ID без токена:
`GET kovaaks.com/webapp-backend/benchmarks/player-progress-rank-benchmark?benchmarkId=<id>&steamId=<steamid>&page=0&max=N`
→ per-scenario `score` + `rank_maxes` (пороги рангов) + `benchmark_progress` +
`overall_rank`. Это тот же бэкенд, что использует evxl.app. Значит Voltaic-ранг
становится **объективно подтягиваемым** сигналом (не self-report): игрок один раз
привязывает публичный Steam ID → движок опрашивает прогресс. Кавеаты интеграции:
read-only публичный роут (профиль-роут требует токен — нам не нужен); уважать
rate-limit + кэшировать; `benchmarkId` маппить по сезону; Steam-профиль должен
быть публичным.

### Обогащение `correction`: фазы флика (порт идеи, не кода)

Идея из родственного `Ngambarde/aim_trainer_analysis` (лицензия **AGPL-3.0** →
берём только *концепцию*, код не копируем). Каждое наведение делится на две фазы:

1. **Ballistic / flick** — начальное баллистическое движение к цели (быстрое,
   open-loop, без визуальной обратной связи). Здесь живёт **перелёт**.
2. **Adjustment / settle** — доводка микрокоррекциями по визуальной обратной
   связи до выстрела (closed-loop).

У них `average adjustment time` коррелирует с результатом сильнее (R²≈0.86), чем
in-game accuracy (R²≈0.28) — эмпирическое подтверждение управляющего принципа
проекта «числа движка важнее внутриигровых».

**Перенос в наш движок бесплатен по данным:** у нас уже есть per-frame offset
прицел↔голова в HU по ходу эпизода (`engine/episodes.py`). Не нужен новый
детектор — только временная сегментация существующего ряда offset(t) внутри
эпизода по порогу «near-band» (аналог их `--flick_radius`, единственная ручка):

- `flick_overshoot_hu` — пиковый выход за цель в ballistic-фазе (уточняет текущий
  `correction`: сейчас меряем итог, добавляем — как флик к нему пришёл).
- `settle_time_frames` — длительность adjustment-фазы = **новый диагностик**,
  ортогональный placement/consistency (тот, что коррелирует с результатом).
- `settle_jitter_hu` — остаточная дисперсия в adjustment-фазе → сигнал
  «рывковости», который **триггерит опциональный трекинг-дрилл** (замыкает петлю
  с блоком трекинга выше).

Всё считает движок → принцип «числа только движок» сохранён. Кавеат тот же, что
у текущего `correction`: output-space прокси (видим прицел↔голову, не ввод мыши).

## Этап 2 — петля прогресса (оформлена отдельным спеком)

> Полный дизайн: [2026-07-05-phase2-progress-loop-design.md](2026-07-05-phase2-progress-loop-design.md)
> (фаз-метрики флика, KovaaK's API по Steam ID, двухсигнальная прогрессия).
> Краткая выжимка ниже.

- Хранилище почти бесплатное: `coach_report` уже в `AnalysisSession` (SQLite) с
  `player_id` + временем; при стабильных `drill_id` + сохранённом `baseline`
  история тянется запросом.
- Новая секция `drill_progress` в evidence-JSON (движок): `delta = current −
  baseline` + `confidence` (те же пороги `MIN_*`).
- **Без каузальности:** движок отдаёт дельту+confidence; VLM говорит «движется в
  нужную сторону», НЕ «дрилл сработал» — адхеренс/конфаундеры неизвестны.
- Порядок клипов: `recorded_at` = время загрузки, не съёмки → caveat; лучше
  опц. поле даты съёмки в форме.
- Прогрессия: улучшение сверх критерия с confidence → tier+1; регресс/стагнация
  с confidence → держим/поднимаем приоритет; мало данных → CTA «ещё клип».

## Будущий план реализации

**Фаза 1 — каталог + детерминированные критерии** (самодостаточна, закрывает дыру валидации):
1. `coach/drill_catalog.py`: типы + каталог + `assemble_drill()`. TDD.
2. `schema.py`: `DrillSelection` + сборка финального `Drill` движком.
3. `report.py`/pipeline: `SuccessCriterion` из `values`, сборка дриллов после парса.
4. `validate.py`: проверка `drill_id`↔каталог↔finding; снять number-check с критерия.
5. `prompt.py`: меню каталога + правила выбора.
6. Правило урезки плана при отсутствии диагнозов + CTA.
7. Frontend `DrillTable`: критерий-строка от движка, «главный дрилл» наверх.
8. Тесты: каталог, критерии на реальных `values`, валидатор (несуществующий id,
   метрика без finding), урезка плана.

**Фаза 2 — петля прогресса** (свой спек):
1. Секция `drill_progress` в `report.py` (дельты + confidence).
2. Чтение истории назначенных дриллов из `AnalysisSession`.
3. Промпт/валидатор: язык «движется», запрет каузальности.
4. Прогрессия по tier; опц. дата съёмки + caveat порядка.
5. UI-блок «динамика метрики по клипам».

## Принятые решения (2026-07-05)

1. **Схема дрилла — Вариант A.** VLM-выход = `drill_id + priority + rationale`;
   финальный `Drill` (name/platform/dose) + `SuccessCriterion` собирает движок.
   Закрывает принцип «числа только движок» и сокращает выход VLM.
2. **Каталог — принят как стартовый**, пользователь вносит доменные правки
   (имена сценариев, спорные соответствия метрике) поверх выверенной Voltaic-базы.
3. **Выбор tier — движок.** Первый клип всегда tier 1; повышение — прогрессией
   Фазы 2. `DrillSelection` НЕ несёт поле `tier` (схема проще).
4. **`dose_override` от VLM — убран.** Не реинтродуцируем VLM-число; доза только
   из каталога.
5. **Неймспейс `drill_id` фиксируется сразу** (вида `placement_t1_range_preaim`)
   — Фаза 2 ключуется на стабильные id, переименование позже рвёт историю.
