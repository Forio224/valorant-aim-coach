# Дизайн Фазы 2: петля прогресса (progress loop)

**Статус:** УТВЕРЖДЁН по развилкам (2026-07-05); зависит от Фазы 1 (стабильные
`drill_id` + сохранённый `baseline`). Часть ручек калибруется на данных 2A.
**Дата:** 2026-07-05. **Область:** `engine/` (фаз-метрики, `drill_progress`),
`backend/` (история из `AnalysisSession`, интеграция KovaaK's API), `coach/`
(язык динамики), frontend (блок «динамика»).
**Родитель:** [2026-07-05-drill-catalog-progress-design.md](2026-07-05-drill-catalog-progress-design.md) — Фаза 1 (каталог + детерминированные критерии).

## Проблема

Фаза 1 назначает дрилл и записывает `SuccessCriterion` с `baseline`. Но история
метрик по клипам (`engine/profile_store.py`, `coach_report` в `AnalysisSession`)
не используется, чтобы ответить на главный вопрос удержания: **«сдвинулась ли
метрика после совета?»**. Плюс два непокрытых источника сигнала:
- **внутри клипа** — движок меряет только *итог* наведения (`correction` =
  перелетел/недолетел), но не *процесс* (как флик к цели пришёл);
- **вне клипа** — прогресс игрока в аим-тренажёре (Voltaic-ранг) объективно
  доступен по Steam ID, но не подтягивается.

## Цель Фазы 2

Замкнуть петлю: назначили дрилл → игрок тренируется и приносит новые клипы →
движок показывает динамику метрики → коуч честно говорит «движется в нужную
сторону» (без каузальности) → tier растёт по **двум независимым объективным
сигналам**. Плюс углубить портрет фаз-метриками флика на *уже имеющихся* данных.

**Управляющий принцип сохранён:** движок считает дельту и confidence; VLM только
формулирует направление и НЕ утверждает «дрилл сработал» (адхеренс и конфаундеры
неизвестны).

## Зависимость от Фазы 1 (жёсткая)

- `drill_id` стабильны между сезонами/релизами (иначе история рвётся).
- `SuccessCriterion` сохраняется структурно (`{metric, value_key, comparator,
  target, baseline}`) — Фаза 2 читает `baseline` для дельты.
- Каталог с tier'ами Novice/Intermediate/Advanced и порогами рангов Voltaic.

---

## Компонент A — фаз-метрики флика (обогащение движка)

Порт *идеи* из `Ngambarde/aim_trainer_analysis` (лицензия **AGPL-3.0** → берём
концепцию, код НЕ копируем; перереализация в `engine/` с нуля).

Каждое наведение делится по ряду `offset(t)` внутри эпизода (`engine/episodes.py`,
данные уже есть — новый детектор не нужен):
1. **ballistic/flick** — от старта эпизода до первого входа offset в «near-band»
   вокруг цели (open-loop бросок; здесь живёт перелёт);
2. **adjustment/settle** — от входа в band до выстрела (closed-loop доводка).

Новые метрики (все считает движок):
- `flick_overshoot_hu` — пиковый выход за цель в ballistic-фазе (уточняет
  `correction`: было «итог», стало «+ как пришёл»).
- `settle_time_frames` — длительность adjustment-фазы; **новый диагностик**,
  ортогональный placement/consistency (эмпирически коррелирует с результатом
  сильнее, чем in-game accuracy).
- `settle_jitter_hu` — остаточная дисперсия в adjustment-фазе → сигнал
  «рывковости» (триггер трекинг-supplementary, см. компонент E).

Ручка: `near_band_hu` — порог границы фаз (аналог их `--flick_radius`).
Кавеат наследуется от `correction`: output-space прокси (видим прицел↔голову, не
ввод мыши); граница фаз — приближение. Пороги `MIN_*` по числу дуэлей действуют.

## Компонент B — секция `drill_progress` в evidence-JSON

Движок добавляет в отчёт по каждому активному дриллу:
```
drill_progress: [{
  drill_id, metric, value_key,
  baseline,            # из SuccessCriterion прошлого назначения
  current,             # то же value_key на текущем клипе
  delta = current − baseline,
  direction,           # improved | regressed | flat (по знаку с учётом comparator)
  confidence,          # diagnosis | hypothesis | insufficient — те же MIN_*
}]
```
Каузальности нет: только дельта + направление + confidence.

## Компонент C — чтение истории назначенных дриллов

Источник почти бесплатный: `AnalysisSession` (SQLite) хранит `coach_report`
(с `drill_id` + `SuccessCriterion`) и `player_id` + время. Запрос: последние
назначения игрока по `drill_id` → `baseline` для компонента B. Порядок клипов —
по `recorded_at` (см. кавеат ниже).

## Компонент D — Voltaic-сигнал через KovaaK's API (объективный, не self-report)

Публичный роут KovaaK's webapp-backend отвечает **по Steam ID без токена**:
```
GET kovaaks.com/webapp-backend/benchmarks/player-progress-rank-benchmark
    ?benchmarkId=<id>&steamId=<steamid>&page=0&max=N
→ per-scenario score + rank_maxes (пороги рангов) + benchmark_progress + overall_rank
```
(Тот же бэкенд, что использует evxl.app; профиль-роут требует токен — нам не нужен.)

Игрок один раз привязывает публичный Steam ID → движок опрашивает прогресс по
назначенным сценариям. Двойная польза:
- **прогресс механики** — вырос ли ранг на назначенном сценарии;
- **адхеренс-прокси** — играл ли игрок назначенный сценарий вообще (score>0/растёт).

Кавеаты интеграции: read-only публичный роут; уважать rate-limit + кэшировать;
`benchmarkId` маппить по сезону; Steam-профиль публичный; отсутствие Steam ID →
деградация до engine-only сигнала.

## Компонент E — двухсигнальная tier-прогрессия

Два независимых объективных сигнала:
- **(а) перенос** — HU-критерий движка на клипах Valorant (взят ли `target`
  из `SuccessCriterion` с `confidence=diagnosis`);
- **(б) механика** — Voltaic-ранг из API (взят ли верхний ранг тира:
  Novice→Gold, Intermediate→Master, Advanced→Celestial).

Правило:
- оба взяты → уверенное `tier+1`;
- взят один → держим tier, поднимаем/держим приоритет, CTA на отстающий сигнал;
- расходятся сильно → **caveat**, а не молчаливое повышение;
- мало данных (`insufficient`) → CTA «ещё клип / ещё прогон сценария».

Триггер трекинг-supplementary: `settle_jitter_hu` выше порога с confidence →
движок добавляет 1 трекинг-дрилл из опц. блока каталога (без числового критерия),
VLM объясняет «для плавности».

## Компонент F — промпт/валидатор: язык динамики

- Разрешено: «метрика движется в нужную сторону», «ранг вырос до …».
- **Запрещено** (валидатор ловит): «дрилл сработал», «благодаря дриллу»,
  каузальные конструкции — адхеренс/конфаундеры неизвестны.
- Числа дельты/ранга — только из `drill_progress`/API (та же groundedness, что
  в Фазе 1: VLM не изобретает числа).

## Компонент G — UI «динамика метрики по клипам»

- Спарклайн/линия метрики по `recorded_at`, baseline-линия, отметка tier-перехода.
- Два сигнала рядом: HU-тренд (клипы Valorant) + Voltaic-ранг (тренажёр).
- Пустая история (первый клип) → аккуратный empty-state, не ошибка.

## Кавеат порядка клипов

`recorded_at` = время загрузки, не съёмки → возможен неверный порядок. Решение:
опц. поле «дата съёмки» в форме загрузки + caveat, если поле пустое.

## Границы (что Фаза 2 НЕ делает)

- **Не утверждает каузальность** (это не A/B, адхеренс не гарантирован).
- **Не детектит, какой дрилл игрок «играл» внутри клипа Valorant** — клип
  Valorant ≠ прогон тренажёра; адхеренс к KovaaK's-дриллу берётся только из API.
- **Не трекает время тренировки/усилие** — только результат (дельта + ранг).

## План реализации (под-фазы, каждая TDD, самодостаточна)

**2A — фаз-метрики флика** (обогащает движок независимо от петли):
1. `engine/` сегментация `offset(t)` по `near_band_hu`; `flick_overshoot_hu`,
   `settle_time_frames`, `settle_jitter_hu` с confidence по `MIN_*`.
2. Встроить в `report.py` (в existing `correction` finding или рядом).
3. Тесты: синтетические эпизоды (чистый флик / долгий settle / джиттер).

**2B — петля прогресса на engine-сигнале** (без внешнего API):
1. `drill_progress` в `report.py` (дельты + direction + confidence).
2. Чтение истории назначений из `AnalysisSession` по `player_id`+`drill_id`.
3. Промпт/валидатор: язык «движется», запрет каузальности.
4. UI-блок динамики (HU-тренд + baseline + tier-переход).
5. Опц. поле «дата съёмки» + caveat порядка.

**2C — Voltaic-сигнал + двухсигнальная прогрессия**:
1. Привязка Steam ID (форма/профиль игрока); валидация публичности.
2. Клиент KovaaK's API: опрос `player-progress-rank-benchmark`, кэш, rate-limit,
   маппинг `benchmarkId` по сезону; деградация без Steam ID.
3. Правило прогрессии (компонент E): совпали → tier+1, разошлись → caveat.
4. Триггер трекинг-supplementary по `settle_jitter_hu`.
5. UI: второй сигнал (Voltaic-ранг) рядом с HU-трендом.
6. Тесты: мок API (взят/не взят ранг), оба/один/ноль сигналов, нет Steam ID.

## Принятые решения (2026-07-05)

1. **Steam ID — опционален.** Петля работает на engine-сигнале (HU-тренд по
   клипам Valorant); Voltaic-ранг из KovaaK's API — бонус при наличии публичного
   Steam ID. Ядро не блокируется внешней зависимостью.
2. **Дата съёмки — добавляем опц. поле в форму сейчас** (дешевле миграции; иначе
   порядок клипов = `recorded_at` = время загрузки + caveat).
3. **Частота опроса KovaaK's API — по кнопке «обновить прогресс» + кэш** (без
   фонового поллинга на старте; уважает rate-limit).

## Ручки, калибруемые на данных 2A (дефолты)

- **`near_band_hu`** (граница фаз флика) — дефолт: доля от `head_height`;
  финальное значение после прогонов 2A на реальных клипах.
- **Порог `settle_jitter_hu`** (триггер трекинг-supplementary) — задать после
  калибровки; до этого триггер выключен/консервативен.
